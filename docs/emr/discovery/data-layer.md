## Q2: How identity reaches the DB

- **There is no `set_config` / `SET LOCAL` / `request.jwt` anywhere** in lib, app, db, migrations, tests or scripts (grep, 0 hits). There is no transaction-local identity and no `private.current_user_id()`.
- **The RLS identity is `auth.uid()`** (184 occurrences across migrations). It only takes effect for supabase-js clients that carry a user JWT (SSR/browser) and in the RLS test harness.
- **Clinical reads and writes run as the DB owner through Drizzle and bypass RLS.** Scoping is application-level: `resolveEncounterAccess()` (lib/encounter/scope.ts:45) with the bases active_encounter, department_recent (30 days), break_glass and care_team (a seam, always false). Every read and write re-checks it (lib/encounter/record.ts:78-85, :279). PHI reads are logged to `clinical_phi_access_log` (record.ts:326, :450; schema in `db/schema/doctor-workspace.ts`).
- The DB mirror of that rule is `public.has_clinical_relationship(p_patient)` (0040:72-115, SECURITY DEFINER, `auth.uid()`-based, granted to `authenticated`). The 0040 SELECT policies are `patient_user_id = auth.uid() OR user_has_role('superadmin') OR has_clinical_relationship(...)` (0040:148-153). **Patients can read their own clinical_documentation today.** The prompt says patients are denied until Gate CG.
- FORCE ROW LEVEL SECURITY is already used widely (0002:47… and 0040 on every clinical table), but it does not constrain the owner role the app connects as. **Reads do not run as a non-owner role.**
- Writes: server actions use Drizzle directly (`recordClerkshipVersion`, lib/encounter/record.ts:68) and Edge Functions (`ha-start-encounter`, `ha-complete-encounter`, `ha-record-observation`, …).
- **Transactions:** only 6 `db.transaction` sites exist (lib/resus/v2-record.ts:108, app/nurse/resus/\_v2/actions-closeout.ts:270/546/623, app/doctor/\_lib/workspace-actions.ts:246). **`recordClerkshipVersion` is not transactional.** Its read-max-version then insert doc then fan-out inserts (record.ts:90-204) can half-commit. The UNIQUE (encounter_id, version) constraint only catches the version race.

## Q3: Runtime

- **Hosted Supabase only.** There is no `supabase/config.toml`, no local stack and no PGlite. The main tree's `.env.local` was created by the Vercel CLI (DATABASE_URL, DIRECT_URL, SUPABASE keys, PHI key, Sentry) and points at the hosted project (**presumed production**). It sets `ENCOUNTER_ENGINE_LIVE=1`, `NCD_CLERKSHIP_LIVE=1` and `CLERKSHIP_DRAFTS_LIVE=1`, which implies 0040 and 0048 are applied there. This worktree's `.env.local` is labelled "Harness-only: dead database, synthetic keys".
- Connections: the pooler in transaction mode (:6543), `prepare:false`, max 10 in prod / 3 in dev (db/index.ts:26-31). There is no single-connection limit (R7's G1 does not apply). Drizzle-kit needs DIRECT_URL (:5432), which is IPv6-only on the free tier (scripts/migrate.ts:5-9).
- Tests: Vitest. `vitest.config.*` loads `.env.local` by forcing NODE_ENV=development around `loadEnvConfig`, and stubs `server-only`. `tests/_setup.ts` also loads `.env` and `.env.local`.
- **RLS gating:** `tests/rls/_helpers.ts:33-59` sets `RLS_TESTS_ENABLED = MEDSYNC_ALLOW_RLS_DB_WRITES==="1" && all four of NEXT_PUBLIC_SUPABASE_URL, ANON_KEY, SERVICE_ROLE_KEY and DATABASE_URL`. Suites use `describe.skipIf(!RLS_TESTS_ENABLED)` (19 files), and without the flag they SKIP. The helpers create real `auth.users` (service admin API), sign in with the anon client and use `serviceSql` (postgres-js, max 1). The comment at :40-52 warns that running against prod leaves audit rows that cannot be removed. **What E1 needs:** a separate hosted Supabase dev project with synthetic data. Point `.env.local` at it, apply 0000→0070 through `db:migrate`, then set `MEDSYNC_ALLOW_RLS_DB_WRITES=1`. No install is needed. Pure-engine tests need no DB.

## Q11: `lib/encryption.ts` (164 lines, server-only)

| Export             | Signature                             | Notes                                                                                                                 |
| ------------------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `encrypt`          | `(plaintext: string) => string` (:78) | AES-256-GCM, random 12-byte IV, wire format `iv:authTag:ciphertext` (base64, `:`-joined)                              |
| `decrypt`          | `(payload: string) => string` (:97)   | throws on malformed payload, tampering or wrong key                                                                   |
| `blindIndex`       | `(value: string) => string` (:134)    | hex HMAC-SHA-256 keyed by `SHA-256("medsync-blind-index" ‖ PHI key)`, for equality search (`phone_hmac`, 0060:63,100) |
| `generateKey`      | `() => string` (:148)                 | 32-byte base64                                                                                                        |
| `ciphertextsEqual` | `(a, b) => boolean` (:159)            | timing-safe                                                                                                           |

- Key: env `MEDSYNC_PHI_KEY` (base64, 32 bytes; validated in lib/env.ts:33-35), read on every call through `loadKey()`. There is one key only and no key ID in the wire format.
- Rotation: **not implemented.** ADR 0008 §6 (docs/adr/0008-phi-encryption.md:65-79) documents a manual re-encrypt with `MEDSYNC_PHI_KEY_NEW` and defers a `v2:` keyId prefix.
- HMAC: only `blindIndex`, which is **derived from the PHI key**. There is no separate HMAC key, so E10 ("dedicated server key held separately") needs a new env var and a helper.
- A Deno twin, `supabase/functions/_shared/encryption.ts`, is byte-identical and covered by `tests/encryption/cross-runtime.test.ts`.
- **Gap (R8 / Law 10):** `clinical_documentation.section_data` stores the clerkship JSON **in plaintext** (`sectionData: clerkship`, lib/encounter/record.ts:106), although db/schema/encounter.ts and 0040 both claim "PHI free-text encrypted at the app layer". `clerkship_drafts.payload` is also plaintext jsonb (db/schema/clerkship-drafts.ts:31; lib/ncd/draft.ts:98). Resus is the one clinical module that encrypts (lib/resus/record.ts:171, v2-record.ts:164).

## Q14: Signed-reference store

**It is TypeScript files, not a DB table, and there are four different shapes:**

| Module      | File                                                  | Entry shape                                                                                                                                                | Signed marker                                                                                                   |
| ----------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Resus v2    | `lib/resus/reference/ref.ts` (+ 12 catalogs)          | `RefEntry {id, text, value?, unit?, source, url, verifiedOn, confidence: "verified-web"\|"reference-doc-only"\|"design", status: "signed"\|"pending_cso"}` | `refValue(e)` returns `"pending CSO sign-off"` unless the entry is signed; `indexRefs` throws on a duplicate ID |
| Triage      | `lib/triage/reference/{types,catalog,index}.ts`       | `Provenance {source, version}` + `CatalogMeta {catalogVersion, ratifiedOn, ratifiedBy}` (types.ts:13-22)                                                   | catalog-level ratification only                                                                                 |
| Prescribing | `lib/prescribing/reference/emergency-drug-catalog.ts` | `EMERGENCY_DRUG_CATALOG_META {verifiedOn, guidelineCycle, basis, crossCheck}` + per-drug `confidence: DoseConfidence` (:46, :62)                           | confidence, no status                                                                                           |
| NCD         | `lib/ncd/catalog/schema.ts` + `diabetes/*`            | `Citation {standard, version, title, url?, quote?, retrieved?, csoSigned: boolean, …}` (:65-80)                                                            | `csoSigned` (all false today)                                                                                   |

DB-side signing exists only for the patient symptom catalogue: `patient_symptom_catalog_versions` (0066:36-45, `signed_by_user_id`, `signed_at`, status CHECK) plus the `sa-sign-catalog-version` Edge Function.
**Recommendation:** for EMR critical limits, plausibility bounds, HMIS and IDSR, reuse the **resus `RefEntry` + `refValue`** pattern, which matches Law 7 exactly: source URL, verified date, and no number shown until signed. Moving it to a shared `lib/reference/` is a Phase 1 decision.

## Prompt vs repo

1. Prisma, `prisma dev` and PGlite → the repo has Drizzle + postgres-js, hand-written SQL and a custom migrator. **R7 is refuted**: hosted Supabase, pooled, no single-connection limit.
2. pnpm and Node 22 → npm (package-lock) and `.nvmrc` 24.
3. "Interactive transaction + `set_config('app.user_id')` + `private.current_user_id()`" (§7.8) → no such pattern exists. Identity is `auth.uid()` for JWT clients and application-level scoping for owner-role Drizzle. There is no `private` schema function (the helpers live in `public`). E2 would be greenfield.
4. "Reads connect as a non-owner role" → all clinical reads run as the owner and bypass RLS. RLS is defence-in-depth only.
5. "Patient role denied until Gate CG" → the 0040 policies already let a patient SELECT their own documentation, diagnoses and problems.
6. "Writes through audited server actions using the service role" → partly true: clinical writes use owner Drizzle in server actions, and admin/booking writes use Edge Functions.
7. Enum style is text + CHECK, not pg enums. §7.1's split-migration caveat does not apply.
8. HMAC: the only helper, `blindIndex`, is derived from the PHI key. E10's separate key does not exist yet.
9. The signed-reference "store" is four file-based shapes, not one table.
10. Playwright is absent and axe-core is present (jsdom only). There is no print precedent.
11. The prompt's §7 tables are already partly built by 0040 (`clinical_documentation`, `encounter_diagnoses`, `problem_list`, `patient_allergies`, `encounter_orders/results`, `encounter_events`, `care_plan`), 0049 (problem-list synthesis) and 0050/0051 (lab results workflow). "Evolve before adding" applies to these, not only to encounters and `clinical_observations`.
12. **R9 is confirmed and worse:** 0041 already seeds a curated ICD-10 subset (and mirrors it in `lib/encounter/reference-codes.ts`), and `THIRD-PARTY-NOTICES.md` does not exist.

## Risks

- Plaintext clerkship JSON in `clinical_documentation` and `clerkship_drafts`, contradicting the code's own comments and Law 10. Any EMR note store must encrypt before the insert.
- `recordClerkshipVersion` runs without a transaction, so a partial fan-out is possible. EMR sign must be one `db.transaction`.
- The main `.env.local` points at the hosted, probably production, project. RLS probes must never run there, so E1 needs a separate dev project.
- Owner-role Drizzle means every new EMR query needs an explicit tenant and access predicate in code. There is a source-level invariant test precedent at tests/emergency/queries-invariants.
