## 1. Q4 Visit model (intake → triage → assignment → encounter)

| Object                                  | Where                                                                                        | Link columns                                                                                                                                                                                                                                                                                                       |

| Assignment                              | **No table.** A `planned` encounter is the assignment (`lib/encounter/assignment.ts:17-23`). | `encounters.triage_record_id` (0040)                                                                                                                                                                                                                                                                               |

| `queue_entries`                         | `db/schema/scheduling.ts:433+`                                                               | `encounter_id` (`:458`)                                                                                                                                                                                                                                                                                            |

Flow and writers:

1. **Triage.** `app/nurse/triage/actions.ts:151` inserts `triage_records` (service client). `:191-195` sets the intake to `triaged`, and `:207` sets the queue priority. The same action can assign right away (`:261` → `assignDoctorFromIntake`). Rapid-red path: `:324`, `:356`.
2. **Assign.** `assignDoctorFromIntake` (`lib/encounter/assignment.ts:99-240`). It reuses the encounter for that triage if one exists, or the visit's open encounter (`findOpenEncounterToday`), or inserts a `planned` encounter with `encounter_type='emergency'`, `triage_record_id`, `appointment_id` (`:219-236`). Callers: `app/nurse/triage/actions.ts:261,426` and `app/doctor/_lib/workspace-actions.ts:141`. Reassign: `reassignPlannedEncounter` (`:244`, called from `app/doctor/encounters/actions.ts:58`).
3. **Start from triage.** `openEncounterFromTriage` (`lib/encounter/handoff.ts:88-219`). Order: an already-started encounter for the triage is idempotent (`:144`) → today's open visit gets the triage link (`:150-154`) → the planned one moves to `in_progress` with `started_at=now` (`:155-169`) → otherwise insert `emergency` `in_progress` (`:170-185`). Then it seeds a **draft** clerkship version when there is none yet (`:190-213`). Callers: `app/doctor/encounters/actions.ts:31`, `app/doctor/_lib/workspace-actions.ts:157,218`, `app/nurse/resus/_v2/actions-closeout.ts:204`.
4. **Appointment / queue start.** Edge `ha-start-encounter` inserts `in_progress` from an appointment (`supabase/functions/ha-start-encounter/index.ts:153-163`). It does **not** set `encounter_type`, so the default is `opd`. For an appointment-less queue row it goes through `startFromQueueRow`, which inserts `encounter_type:'opd'` (`:311-320`) and links the intake (`:338-343`). Caller: `app/doctor/schedule/actions.ts:125`.
   - Gap: `ha-start-encounter` does **not** check for an already-open encounter. Only the reverse direction is deduplicated (handoff/assign look for the queue-rail encounter, `handoff.ts:40-47`). So a patient who is triaged, handed off, and then called from the rail can get two `in_progress` encounters.
5. **End visit.** See 2.3. It sets `patient_intakes.status='completed'` plus `encounter_id` (`ha-complete-encounter/index.ts:184-195`).

Intake → encounter traversal therefore goes through three different links: `intake.encounter_id` (written at start from the queue row, or at completion), `encounter.triage_record_id → triage.intake_id`, and `encounter.appointment_id = intake.appointment_id`. There is no single visit id.

### 2.3 Complete / end visit

Only one path: `completeEncounterAction` (`app/doctor/schedule/actions.ts:141-164`) calls Edge `ha-complete-encounter`. It requires `in_progress` (`index.ts:90`), then sets state `completed` + `ended_at` + `completion_reason` (`:134-137`). It then cascades: the queue row goes to `done` (`:151`), the intake to `completed` (`:190`), nursing assignments get `ends_at` (`:201`), and the appointment to `completed` (`:215`). UI: `EndVisitButton` in `queue-rail.tsx:189`, `visit-status.tsx:23`, `patient-panel.tsx:233`. The disposition is **not** asked for or written. There is no sign-off and no requirement that documentation exists. A `planned` encounter cannot be completed or cancelled by any action (no writer of `cancelled` found).

### 2.5 `app/doctor/encounters/[encounterId]`

- `page.tsx:32-250`: `requireDoctorScope` → returns a dark note unless the engine is live (`:36`). It selects the encounter (`:58-69`) with a hospital check (`:71`), then runs `loadEncounterRecord` (access and audit, `:82`) and `fetchPatientSummaryAudited` (`:92`). Under the NCD flag it runs `loadLatestVitals` (reads both `clinical_observations` and `triage_records.vitals_snapshot`), `loadPatientDemographics` and `loadNcdDraft` (`:106-132`), then renders `NcdClerkship` (`:192-220`). Otherwise it shows a "Being rebuilt" card with the last doc version (`:221-240`).
- **What it stores today: only `clerkship_drafts`.** `saveNcdDraftAction` (`actions.ts:29-51`) checks the flag and that the hospital matches. It does **not** check encounter state (so drafts can be written after completion) and does **not** call `resolveEncounterAccess`. It then calls `saveNcdDraft` (`lib/ncd/draft.ts:98-124`), which upserts on (encounter_id, author_id) with payload `{kind:'ncd_capture', catalogId, catalogVersion, values}`. The load (`draft.ts:55-90`) drops keys the catalogue no longer knows. `clerkship_drafts` has **no FK** to `encounters` (`0048_clerkship_drafts.sql:18`, `clerkship-drafts.ts:28`). The comment says drafts are "deleted on explicit save" (`clerkship-drafts.ts:13`), but no explicit NCD save exists, so nothing deletes them.

## 3. Q6 `clinical_observations`

Schema: `db/schema/nurse-workspace.ts:114-163`. Created in `0031_nurse_workspace.sql:139`; `acvpu` + `triage_record_id` added in `0036_triage_engine.sql:229-242`; `etco2`, `urine_output` added in `0038_resus_abcde.sql:367-376`.
Columns: id, hospital_id, patient_user_id, encounter_id (nullable, set null), recorded_by_user_id, observation_kind, numeric_value_1, numeric_value_2 (BP diastolic), unit, pain_scale, notes (plain text), recorded_at, state ∈ `active, corrected`, corrected_by_observation_id (self-FK), triage_record_id, created_at, updated_at. Triggers: `updated_at` and `audit_log_changes` (`0031:201-209`). **Not insert-only.** RLS is forced (`0031:178-179`).
**Drift:** the Drizzle `obs_kind_check` (`nurse-workspace.ts:153`) lacks `etco2`, `urine_output`, which the SQL (0038) allows and resus v2 writes (`lib/resus/v2-rules.ts:249-250`). `db:check` / `db:generate` would try to narrow the constraint.

**Correction flow.** The only correction is the resus v2 `retractMirror` (`actions-survey.ts:344-363`), which runs an **UPDATE `state='corrected'` in place**. | status (6 values)                                                          | `active` / `corrected`                                               |
| sensitivity                                                                | absent                                                               |

| note_ciphertext (encrypted)                                                | `notes` plaintext                                                    |

BP is stored as one row holding two values; CFC would store it as two concepts, or as one with components. Migration path: a new CFC table, with a backfill/dual-write from these three writers plus the triage snapshot. `clinical_observations` cannot be reshaped in place into an insert-only table without breaking `retractMirror`.

## 5. Harmonisation notes (for the plan, not decisions)

1. The NCD clerking has no route into the record. A finalise action has to write `clinical_documentation` (final) and then CFC facts, and delete the draft. `recordClerkshipVersion`'s fan-out assumes the v1 `Clerkship` shape, not `CaptureMap`.
2. End-visit should require or offer a disposition and a sign-off state. `completion_reason` is a constant today.
3. Unify the visit key. The intake links to its encounter through three different paths (section 1), and `ha-start-encounter` lacks the open-encounter dedupe.
4. Observations: triage vitals and resus mirrors carry no `encounter_id`. Any per-encounter chart must join by patient and time.
5. `recordClerkshipVersion` should be transactional, and allergies should be de-duplicated. Also fix the Drizzle `obs_kind_check` drift.
